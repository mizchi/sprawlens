# Sprawlens formalization

Sprawlensの実行実装はTypeScript / JavaScriptに置き、ここでは論文の中心contractを実装詳細から独立したLean 4の定理として管理する。LeanからJavaScriptを生成せず、手書きTypeScriptとの対応は`claims.json`と共有conformance fixtureで監査する。

## Pinned environment

- Lean: `v4.33.0`
- Mathlib: `v4.33.0` (`db584cd6d46c92f209a44c0f1c829460d327499d`)
  - L0の抽象relationとL1–L2はMathlib非依存。
  - 実行可能な有限selector、exact rational adjacency slack、L3のfinite geometry / algebraに使用する。

just lean-check

## Current model

`Sprawlens.FeasibleEnvelope`はcandidate、constraint score、selection costの具体型を仮定しない。有限候補集合、validity predicate、複数constraint floor、cost最小性、baseline fallbackだけを扱う。

baselineがeligibleなら、任意のselection resultについて次を証明済みである。

- selected candidateは宣言した有限集合の要素である。
- selected candidateはvalidである。
- selected candidateは全constraint floorを満たす。
- selected costはbaseline cost以下である。

eligible集合が空の場合はbaselineへfallbackする。baseline自身がinvalidならresultもinvalidになりうるため、「全resultがvalid」は成り立たない。この反例をLean file内のwitnessとして保持する。

`Sprawlens.FeasibleEnvelopeSelector`は、costとtie-break keyの全順序から有限候補を決定的に選ぶ実行可能関数を定義する。eligible候補があればその最小要素、なければbaselineへfallbackし、その戻り値が常に上記abstract relationの`IsResult`を構成することを証明した。共有fixtureを読むLean checkerもこのselectorを使う。TypeScriptのsort実装全体、candidate生成、solver convergenceの正しさを証明したものではない。

`Sprawlens.Paper1Contract`はこの一般relationと実行可能selectorを第一論文のprimary policyへ特殊化する。candidateはexact rational adjacency、exact rational displacement、convergence flagを持ち、zero-tolerance adjacency floorとdisplacement costを使う。baseline membershipとbaseline convergenceの下で、selectorが返すcandidateの収束、baseline以上のadjacency、baseline以下のdisplacementを個別に証明した。論文中のdominance contractはこの三定理に対応する。

`Sprawlens.AdjacencyRate`はTypeScriptの`realizedEdgeRate`を、eligible edge数とrealized edge数のexact rational比としてモデル化する。比較用の数値slack `10^-12`が一辺分のscore量子より小さければ、slack付き判定を通ったcandidateはbaselineよりrealized edge数を減らせない。したがって両candidateが同じ正のeligible edge分母を持ち、その分母が`10^12`未満なら、この離散的な非劣化を証明できる。TypeScriptでは分母計算を`eligibleEdgeCount`へ分離し、同じedge listとnode domainならcandidate geometryに依存しないことを回帰testで固定した。分母がちょうど`10^12`なら一辺の損失がslackと同値になる反例も保持する。これはIEEE-754演算一般のrefinement proofではない。

`Sprawlens.ControlledPaths`は第二論文のcontrolled sequenceを離散graphとして一般化する。no-op / reversalの始終端同値性、weight変更とleaf追加、weight変更とedge rewireの可換性を証明した。graphはlistで保持するため、AB/BAの終端同値性はnode、weight、edge、request orderの完全一致である。これは同じ入力graphへ至ったlayout geometryが一致するという主張ではなく、その差をpath dependenceとして識別できるための前提だけを証明する。

`Sprawlens.LayoutConfluence`は編集列を左から実行する一般の状態遷移modelを定義し、独立編集の局所squareがすべて可換なら、隣接する独立編集のswapで結ばれた任意の編集列が同じ終端状態を持つことを証明した。逆方向のload-bearing witnessとして、resetとflipからなる二状態modelでは一つの非可換squareだけで二編集pathの終端が異なることも固定した。これはSprawlensの実layout transitionが可換または非可換だという証明ではなく、その判定を局所squareへ分解する一般contractである。

`Sprawlens.ControlledPathConfluence`はweight変更、leaf追加、rewireを一つのgraph edit言語へ埋め込み、`ControlledPaths`の局所可換性を一般contractへ接続する。これにより、独立swapで結ばれた任意長のcontrolled edit列が同じ入力graph終点を持つことを証明した。ここでもlayout geometryは状態に含めていないため、同一graph終点で異なるgeometryが得られる可能性は意図的に残る。

`Sprawlens.HistorySelectorConfluence`はその可能性を、二候補・二つの可換な入力編集・前状態への距離を最小化する有限selectorで具体化する。候補をcurrent inputでfilterし、既存の検証済み`FeasibleEnvelopeSelector.minimum?`で前状態距離を最小化する実行可能selectorが、明示的なnearest-predecessor仕様と全Bool入力で一致することも証明した。AB/BAの入力projectionは完全一致するが、各中間入力で一意に選ばれた候補を共通終点のzero-displacement候補として保持するため、最終selected geometryと全状態が異なる。これは実candidate generatorや実数metricの反例ではないが、path dependenceに多数候補や数値誤差が不要であることを示す最小抽象witnessである。

`Sprawlens.SameEndpointConsistency`は、内部状態からcurrent inputを取り出すprojectionと、比較対象のgeometryを取り出すobservationを分離する。任意の二経路について、同じinput終点と異なるobservationを同時に満たす場合だけsame-endpoint violationとし、metric上ではこれが正のpath defectと同値であることを証明した。有限selector witnessはこの定義に対する反例となるため、抽象system全体のsame-endpoint consistencyを否定する。さらにAB/BA commutator defectと二方向のreversal-loop defectを同じpath metricから定義し、二つのloop defectの差の絶対値がcommutator defect以下であること、片方向が初期observationへ完全回復する場合は他方向のloop defectがcommutator defectと一致することを証明した。noise floorとmarginを引いて0で切る`excessDefect`についても、非負性、0となる閾値条件、正となる閾値条件を証明した。加えてpath defectとnoise floorの各区間から`D_excess`を包む区間を作る端点規則と、pointwiseな区間が非空有限集合上の算術平均後も真値を包むことを証明した。derived区間幅はpath幅とnoise幅の和以下であり、両方がtarget以下なら`2 * target`以下となる。このためsampler targetをSESOIから事前に逆算できる。TypeScript contract層の`selectAdaptiveHausdorffTargetFromSesoi`は、事前候補のうち`target ≤ SESOI / 4`を満たす最大値だけを選び、観測effectを入力に取らない。これによりderived sampling幅をSESOIの半分以下に抑えつつ、事後的な精度選択をAPI境界で避ける。ただしSESOI値そのものの科学的決定、実graph digest、canonical geometry、noise floorの推定妥当性、production layoutの経験的欠損値はこの定理の外側である。

TypeScript development runnerは同一seed・同一pathの独立rerunを生成し、repository・condition内の95% empirical nearest-rank値をnoise floorとして`excessDefect`と同じ式へ入力する。入力endpointはnode / edge配列順、node ID、weight、hint、edge source / targetを署名化し、全reversalとAB/BA終点をlayout前にfail-closedで検査する。hierarchyは現行graph schemaに存在しない。same-endpoint cell ID集合、非空boundary、有限座標も集約前にfail-closedで検査し、seed平均→sequence平均→repository summaryの順を固定した。探索用のsampled mean出力は`developmentReliability`に残し、contract targetにはedge-local polygon samplerの`estimate ≤ exact ≤ estimate + additiveErrorBound`をstable-cell平均・clip正規化した区間を使う。D_comm、D_loop、D_repeat、D_excessの全経路と後続平均で下界・上界を別々に保持し、`confirmatoryReliability`として出力する。この対応が保証するのはexact-real離散化区間であり、IEEE-754 roundoffは含まない。

`Sprawlens.EmpiricalQuantile`は固定長tupleを実際にsortしてzero-based順位を選ぶnearest-rank関数を定義する。その出力が「少なくともrank個が結果以下、rank個未満が結果より小さい」というone-based個数characterizationを満たすことを証明した。このcharacterizationから、標本ごとの下界・真値・上界に同じ順位を適用するとquantileも対応する端点区間に入ることが従う。Leanの`Int`実行器とTypeScriptは、unsorted入力、duplicate、singleton、確率1を含む5ケースを共有する。これは有限fixture correspondenceであり、JavaScript sort一般のrefinement proofではない。

`Sprawlens.ComposedApproximateReliability`は、二段のprimitive誤差を加算し、one-sided orderを推移させる。report permissionの下方閉性と合わせ、独立に検証した複数近似段の合計budgetからtarget保存を導く。

`Sprawlens.FiniteApproximationChain`は、非負stage budgetを持つ任意有限chainをendpoint contractへflattenし、chain連結でbudgetを加算する。total 0ならsearch全体が一致し、totalがreportに許可されれば二側・one-sidedのtargetを保存する。

`Sprawlens.DirectedApproximationChain`は、各stageのoverestimateまたはunderestimate orderを同方向に合成してendpoint orderを自動導出する。これによりstage-local certificateだけから任意有限pipelineへone-sided半径を適用できる。

`Sprawlens.PathwiseTargetReliability`は、非一様なprimitive error関数をpointwiseに加算合成し、近似Dijkstraが実際に選んだpathとexact-best比較pathのerror和を返す。二側では両pathの実error和、overestimateではbest比較path、underestimateでは選択pathだけが計算済みmargin未満ならtarget identityが保存される。到達class数を掛ける一様worst-case boundを使わないinstance-specific certificateである。

`Sprawlens.PathwiseApproximationChain`は、このedge-local error関数を任意有限stageへ一般化する。chain連結はerror関数をpointwise加算し、endpoint contractへflattenできる。同方向のstage-local orderもendpointへ合成され、二側・overestimate・underestimateのpathwise margin certificateを有限pipelineへ直接適用できる。

`Sprawlens.PathwiseUniformDominance`は、edge-local errorが一様上限`ε`を持つ場合、具体path errorがまず`path length × ε`、次に従来の`reachable class size × ε`以下になることを証明する。二側・one-sidedの従来margin ruleはすべてpathwise certificateを経由してtarget保存へ因数分解できる。逆は一般に成立せず、pathwise条件だけが通る数値witnessも保持する。

`Sprawlens.PathwiseStrictImprovementWitness`は、そのstrictnessを実行可能な二要素swap graphで実現する。別の三要素contextが誤差1を実現するためglobal uniform boundは必ず1以上だが、対象sourceのbest/selected pathは0-step・error 0である。computed marginは1なので二側・one-sidedのuniform ruleはいずれも失敗し、pathwise ruleだけがverified Dijkstraの保存targetをcertifyする。

`Sprawlens.PathwiseNontrivialImprovementWitness`は0-step退化を除く。三編集のsourceは非normalで、exact/approximate Dijkstraはいずれも一回swapしてcost 1のbestへ到達し、second-targetは別の一回swap path・cost 2、margin 1になる。best error pathは長さ1でもcost 0で、到達不能な長prefix contextが強制するglobal `ε ≥ 1`により旧uniform ruleだけが失敗する。

`Sprawlens.ReachableErrorEnvelope`は、このstrictnessの射程を補正する。error上限をsourceからtrace-equivalentなprimitive contextだけへ制限しても、forward/backward edgeと任意pathの`count × ε`、class-size margin上界を証明できる。上の非退化witnessではglobal envelopeは1以上だがreachable envelopeは0なので、pathwiseはglobal uniformより真に鋭い一方、tightなsource-reachable uniform ruleも同じ判定を回収できる。

`Sprawlens.ReachablePathwiseStrictWitness`は、誤差1を同じreachable component内のsecond-target edgeへ移す。reachable uniform envelopeは必ず1以上になり二側・one-sided ruleは失敗するが、実際に選択・比較される長さ1のbest path errorは0である。従ってpathwise certificateがtightなsource-reachable uniform envelopeより真に鋭くなり得ることを、非zero pathのverified Dijkstra instanceで実現する。

`Sprawlens.PathwiseCertificateIncompleteness`は逆方向の境界を固定する。best edgeをmarginと同じ1だけoverestimateすると、approximate bestとsecondはともにcost 2でtieし、strictなpathwise条件は失敗する。それでもverified Dijkstraの決定的tie-breakはexact bestを返す。従ってcertificate成功はtarget保存の十分条件だが、失敗はtarget変更を意味しない。

`Sprawlens.PathwiseReliabilityVerdict`は、この境界をAPIへ固定する。modeごとに必要errorを導出し、verdictは`certifiedStable | inconclusive`だけを持つ。`unstable` constructorは存在せず、verdictもreport入力から計算される。certifiedなら既証明のstability implicationからtarget一致を導ける一方、inconclusiveかつtarget一致の実Dijkstra witnessも保持する。

`Sprawlens.PathwiseErrorValidity`は、reportへ渡すerror値の健全性をproof-carrying境界にする。`WithinBy`は絶対値を上から抑えるためprimitive errorを非負にし、その和である任意の具体path errorも非負になる。検証済みreportのcertified判定は必ず正のmarginを要求する。生reportへerror `-1`を注入すればmargin `0`でも誤認定できる反例を保持する一方、そのdataから検証済みreportは構成できない。既存のpositive-margin成功例とmargin境界のinconclusive例は、どちらもこの境界を通して元のverdictを保つ。

`Sprawlens.PathwiseReportProvenance`は、非負なscalarだけを任意入力できる残りの隙間を閉じる。mode-indexed evidenceが、二側ではselected/comparison両path、overestimateではcomparison path、underestimateではselected pathを、reportに記録されたsource・target・error costへ型で結び付ける。近似contractと合わせたprovenanced reportは従来のvalidated reportへverdictを変えずに降格できる。strict成功例と境界inconclusive例は実path付きで構成でき、負errorのraw reportには任意の有効contract下でprovenanceを付与できない。

`Sprawlens.PathwiseClassificationReport`は、exact classifierとapproximate searchを同じreportへ接続する。二側・overestimate・underestimateの各分類定理から、approximate searchが実際に返したNormal target、exact classifierのbest targetとmargin、mode別error path provenance、およびcertified時のtarget一致を同時に持つreportが存在する。certifiedならsearch結果がexact bestを返すことをAPI fieldだけから導ける。strict witnessはcertified、margin境界witnessは完全なprovenanceを持ちながらinconclusiveかつbest保存になる。元のpath定理がProp-valued existentialなのでこの接続は論理的存在証明であり、実行可能certificate extractorではない。

`Sprawlens.WeightedPathDataVerifier`と`Sprawlens.PathwiseSerializableReport`は、その実行境界に最小のchecker contractを置く。payloadは各stepのclaimed costとnext vertexだけを持ち、checkerは現在vertexのprimitive-step列挙と照合しながらcount・総cost・終点を再計算する。cost equalityがsoundなら受理結果から同じcount・cost・source・targetの`WeightedTracePath`を復元でき、逆に任意の論理pathには受理されるstep列が存在する。mode別serializable reportは受理済みstep dataからprovenanced reportへ昇格でき、負error forgeryは通らない。strict例の`[(0, best)]`はcertified、境界例の`[(1, best)]`はinconclusiveとして実際にcheckerを通る。Leanのexact-real equalityは非計算的なので、productionではserialized numeric domainのequalityとそのrefinementが別義務になる。

`Sprawlens.EncodedWeightedPathDataVerifier`と`Sprawlens.EncodedPathwiseSerializableReport`は、payloadを`ℝ`へ先にdecodeする制限を除く。primitive cost列挙、等値判定、zero、加算、総costのすべてを任意の`DecidableEq` encoded domainに残し、decodeがzeroと加算を保つときだけ実数modelのpathへ移す。受理countはpayload lengthと必ず一致し、任意の実数model pathにはdecode後costが一致するencoded payloadが論理的に存在する。`Sprawlens.EncodedPathDataWitness`では`Int`を使い、strict例の正しいcost 0と境界例の正しいcost 1を受理し、それぞれ1へ0、0へ1と改竄したpayloadを拒否する。受理reportはdecode後もcertified/inconclusive verdictを保存する。これは整数化できるwitnessのload-bearing instanceであり、production浮動小数点costが整数だという主張ではない。

`Sprawlens.FixedPointEncodedCost`は、encoded domainの現実的候補として正のscaleとunbounded signed integer unitsからなる固定小数点型を定義する。等値判定・zero・加算は整数上で実行可能で、実数decodeは加算をexactに保存する。whole integerは`units = value × scale`でexactに往復する。`Sprawlens.FixedPointPathDataWitness`のscale 1000 instanceでは、strict例の0 unitsとboundary例の1000 unitsを受理し、前者へ1 unitを加える改竄と後者を999 unitsへ減らす改竄をともに拒否する。1 unitのdecode差はexactに`1/1000`で、report verdictもprovenance変換後まで保存される。これはJS `BigInt`互換のcertificate表現候補を示すが、production floatをscale 1000へ丸めてよいという量子化誤差の証明ではない。

`Sprawlens.FixedPointQuantization`は、非負errorを`ceil(error × scale)` unitsへ切り上げる安全側の量子化を定義する。decode後の値は元error以上で、one edgeあたりの過大分は一quantum未満、任意pathではquantized totalが元total以上かつ`path length × quantum`以下の追加に収まる。従って量子化済み二側・overestimate・underestimate reportがcertifiedなら、元の実数reportもcertifiedでtarget soundnessを保つ。逆方向は成立しない。`Sprawlens.FixedPointQuantizationWitness`ではscale 1000、実error `0.0005`、margin `0.00075`を使い、元reportはcertifiedだがerrorが`0.001`へ切り上がったreportはinconclusiveになる。安全な量子化はfalse certificationを作らない一方、certificate powerを失い得る。

`Sprawlens.FixedPointScaleSelection`は、このpower lossが有限pathとstrictly positiveなmargin gapに対して不可避ではないことを示す。任意の有限slack budgetと正gapには`budget × quantum < gap`を満たす有限positive integer scaleが存在する。従ってactual pathwise reportがstrictにcertifiedなら、overestimate・underestimate・二側のいずれでも量子化後certificationを保つscaleが存在する。half-milli witnessもscale 1000ではinconclusiveだがscale 5000ではquantized error `0.0006`となりcertifiedへ戻る。これはscale存在性と十分条件であり、最小scale、payload size、runtime cost、production acceptance rateを同時最適化するalgorithmではない。

`Sprawlens.FixedPointScaleAlgorithm`は、margin gapが`gapUnits / baseScale`として既に整数符号化されている場合に、実行可能な最悪ケースscaleを与える。path edge数を`pathCount`とすると、strict slack条件は`pathCount * baseScale < gapUnits * denominator`であり、その条件を満たす最小の自然数分母が`floor(pathCount * baseScale / gapUnits) + 1`であることを十分性・最小性の両方向から証明した。さらに任意の分母が十分であることとselector以上であることを同値にし、selectorが十分集合のleast elementであることを固定した。出力は常に`pathCount * baseScale + 1`以下で、この上界はgapが1 unitのときtightである。直前のquotient分母はstrict条件に必ず失敗する。gapが0 unitsの場合、十分な分母は存在しないのにNat除算式自体は1を返すため、正gap検査なしに返値をcertificateとして扱ってはならない。この整数条件は実数上の`pathCount × quantum < decoded gap`へ移り、選んだscaleでpathを再量子化すればone-sided両方向とtwo-sided reportがcertifiedになる。たとえば`pathCount = 1`、`baseScale = 4000`、`gapUnits = 1`では4000がstrict境界で失敗し、4001が最小の十分分母になる。ただしこれは一edgeごとの「一quantum未満」を使う最悪ケース条件の最小値であり、具体的なcostが格子点へ整合する場合の最小成功scaleではない。また、複数候補scaleのpayload・CPU・実測acceptanceを同時最適化するpolicyでもない。

`Sprawlens.FixedPointGapEncoding`は、実数margin gapから上の整数selectorへ入る境界を安全側に閉じる。正のbase scaleで`floor(gap × baseScale)` unitsへ切り下げると、decode後gapは元gap以下で、失う量は一base quantum未満になる。符号化後unitsが正なら、その値から選んだscaleのpath slackは元の実数gapより真に小さく、三report modeすべてのcertificationへ接続できる。正unitsが残る条件は`base quantum ≤ gap`と同値で、任意の正gapにはその条件を満たす有限base scaleが存在する。一方、gap `1/2000`をbase scale 1000で符号化すると0 unitsへ消えるため、非零検査はload-bearingである。base scale 4000では2 unitsが残り、一edgeの最悪ケースselectorは2001を返す。これはIEEE-754から数学的floorを正しく計算するparser/refinementをまだ証明せず、符号化gapが0になった場合をcertifiedとして扱うことも許さない。

`Sprawlens.FixedPointCheckedScale`は、このload-bearing前提を返値の型へ反映した実行可能なfail-closed wrapperである。raw自然数入力では`baseScale > 0`かつ`gapUnits > 0`の場合にだけ`some scale`を返し、`none`はどちらかが0であることと同値になる。返却scaleは十分条件を満たす最小分母であり、既証明のresource上界も継承する。実数gap wrapperは`base quantum ≤ gap`の場合にだけ成功し、失敗は`gap < base quantum`と同値である。成功時には元の実数gapに対するstrict slack、量子化path、overestimate・underestimate・two-sided reportのcertificationを、`some scale`の証拠と一緒に返せる。scale 1000のhalf-milli gapは`none`、scale 4000では分母2001の`some`になる。これはLean上のOption APIであり、JS implementation/refinementそのものの証明ではない。

`Sprawlens.FixedPointIntegerReport`は、同一scaleのmargin・selected error・comparison errorをsigned integer unitsのまま保持し、加算とstrict比較だけで実行可能なverdictを返す。正scaleで割るdecodeはstrict orderを完全に保存するため、整数verdictは既存の実数reportをdecode後に評価したverdictと全入力で一致する。two-sidedは`selectedUnits + comparisonUnits < marginUnits`、one-sided二方向は対応する一方のunits比較と同値である。999/1000 unitsはcertified、1000/1000境界はinconclusiveになる。一方、signed integer化だけではvalidityは得られず、comparison error `-1`、margin `0`は整数比較でも偽certifiedになる。そのreportは別定義のnonnegative predicateを満たさない。従ってproductionではinteger comparatorを受理済みpath payloadと非負性検査の後段でのみ使う必要があり、unbounded Lean `Int`との対応にはJS `BigInt`を使う。有限幅整数のoverflow-free性やJS実装自体は未証明である。

`Sprawlens.FixedPointSerializableIntegerReport`は、その後段という順序をproof-carrying typeで固定する。integer reportに`WithinBy` contractとmode別のaccepted fixed-point path payloadを同伴させ、既存のencoded serializable reportとprovenanced reportへ変換する。accepted path evidenceからdecode後の両errorが非負になり、正scaleのorder reflectionによってinteger units自体も非負になる。従ってrequired unitsも非負で、certifiedならmargin unitsは正である。integer verdict、decode後verdict、provenanced verdictは一致する。既存のzero-error accepted pathはinteger reportでもcertified、unit-error境界pathはinconclusiveを保つ。任意のcost model・sourceに対し、`-1` errorのnegative integer forgeryと同じreportを持つserializable/provenanced objectは存在できない。これでinteger comparatorの前にpath acceptanceとvalidityを置く論理順序は閉じたが、production parserとJS checkerのrefinementは引き続き未証明である。

`Sprawlens.FixedPointMarginProvenance`は、error側を完全に検証してもmargin fieldが未拘束だった残りの穴を閉じる。真正なunit-error boundary path、`WithinBy`、非負units、provenanceをすべて保持したまま、actual margin 1000 unitsを1001 unitsへ増やすとraw integer/provenanced reportはcertifiedになる反例を構成した。actual strict premise `1 < 1`は偽である。対策としてreal classifier marginを`floor(margin × scale)`へ切り下げるcanonical encodingを定義し、decode値が元margin以下、lossが一quantum未満、unitsが常に非負であることを証明した。serializable reportのmarginをこのencodingへ型で結ぶwrapperでは、integer certifiedから`required decoded error < actual margin`とtarget soundnessが従う。1001-unit改竄reportはactual margin 1に対するwrapperを構成できず、既存のzero-error例はcertified、unit-error境界例はinconclusiveを保つ。productionではmarginをclient supplied scalarとして信用せず、exact classifier outputとscale tagからtrusted側で再符号化する必要がある。

`Sprawlens.FixedPointScaleTag`は、Leanの型引数が暗黙に保証していた「全numeric fieldが同じscale」をserialized境界で明示する。raw tagged reportがtagを無視してunitsだけ比較すると、scale 500のerror 999 unitsとscale 1000のmargin 1000 unitsは`999 < 1000`でcertifiedになるが、decode後は`999/500 > 1000/1000`なのでactual premiseは偽になる。trusted schemaのexpected scaleに対してmargin・selected error・comparison errorの三tagをすべて検査するparserを定義し、成功が三tag一致および対応するtyped report生成と同値、失敗がいずれかのtag不一致と同値であることを証明した。上のmixed-scale reportはどのexpected scaleでも拒否され、全field scale 1000の999/1000正例は受理される。受理後のtyped verdictはraw units verdictおよびreal decode verdictと一致する。productionではreport-level version/scaleだけでなく、fieldやpath payloadが別scaleから混入しないschema boundaryが必要である。

`Sprawlens.FixedPointTaggedPathVerifier`は、その検査を各serialized path edgeへ拡張する。全step cost tagがtrusted expected scaleと一致するという再帰predicateを先に判定し、成功時だけtagsを除去して既存encoded path verifierへ渡す。parser成功は全tag一致とhomogeneous step列生成の組に同値で、step数とtarget列を保存する。合成checker成功からdecode後の genuine `WeightedTracePath`が従い、返却countはraw step lengthと一致する。反例ではscale 500・1000 unitsのboundary stepからtagを先に捨てるとscale-1000 typed verifierがcost 1として受理するが、安全なcheckerは拒否する。scale 1000・1000 unitsの同型stepは受理される。従ってreport fieldだけでなく全edge tagをpath verification前に検査する必要があり、unitsへparseしてから元tagを忘れる順序は不正である。

`Sprawlens.FixedPointResourceLimits`は、unbounded `Int` / `BigInt`を選んでも残るresource exhaustion境界を明示する。raw pathに最大step数と各signed unitsの`natAbs`上限を課し、そのdecidable guardをtag検査・path verificationより先に置く。bounded checker成功はlimit成立とunderlying checker成功の組に同値で、genuine decoded path、raw count一致、`count ≤ maxSteps`が従う。limit内dataについてはunderlying checkerの結果を完全に保存する。report三fieldにも同じmagnitude guardを置き、成功後のtyped reportへ上界を移送し、decode verdictを保存する。1 step・1000 unitsのboundary pathはlimit `(1,1000)`で受理され、maxSteps 0またはmagnitude 999では拒否される。999/1000のcertified reportもmargin上限999では拒否されるが、数学的verdict自体はcertifiedのままである。従ってresource refusalは`inconclusive`や`unstable`ではなく、別のtransport/policy errorとして扱う必要がある。

`Sprawlens.FixedPointCanonicalDecimal`は、JSON互換のdecimal integer stringをtyped fixed-point costへ移す構文境界を閉じる。標準parserの成功だけでは`01`、`-01`、`-0`のような同値aliasが残るため、parse結果の`Int.repr`と入力文字列のbyte-for-byte一致を追加で要求する。任意の整数reprが受理され、受理文字列はそのreprに一意であること、rejectがcanonical representation不在と同値であることを証明した。文字数guardに加え、外部payload向けには`utf8ByteSize` guardを整数parseより前に置き、受理からbyte上限とcanonicalityを同時に得る。expected scale tagとの一致も先に検査し、成功条件を「tag一致・UTF-8 byte上限・結果unitsのcanonical repr」と完全同値化した。`0`、`123`、`-123`、scale 1000の`999`を受理し、leading zero、`-0`、plus sign、空白、byte超過、異scaleを拒否する。非ASCII `é`が2 bytesで1-byte policyに拒否されることも固定した。production全payloadのbyte上限、およびJS `BigInt` parserとのrefinementは未証明である。

`Sprawlens.FixedPointCanonicalArtifact`は、この単一field contractをraw path step列とreport三fieldへ持ち上げる。path decoderはraw step数を最初に制限し、各costのUTF-8 byte数・canonical decimal・expected scaleを検査してからhomogeneous typed step列を作る。成功の存在は「step数上限かつ全stepがwell-formed」と必要十分で、typed step列のserializationは各reprがbyte上限内ならround-tripする。これを既存encoded path checkerへ接続し、受理からgenuine decoded `WeightedTracePath`と`count = raw.length`を導いた。canonical `1000`は受理され、`01000`、異scale、byte超過、step数超過はgraph verification前に拒否される。report decoderも三fieldすべてについて同じacceptance contractを持ち、modeとtarget metadataを保存し、typed reportをround-tripする。leading zero、`-0`、mixed scale、byte超過を拒否する。一方canonicalな`-1`は構文として正しく受理され、既存のnegative-error forgeryはなおraw integer verdictを偽certifiedにする。従ってcanonical syntaxはnonnegative path provenanceの代替ではなく、その前段だけを閉じる。

`Sprawlens.FixedPointCanonicalProvenance`は、その前段を既存のproof-carrying provenanceへend-to-endで接続する。raw payload shape自体をmode-indexedにし、two-sidedはselected/comparison二path、overestimateはcomparison path、underestimateはselected pathだけを持つ。各pathの再計算costとendpointがreport fieldに一致することを検査し、one-sidedで未使用のerror fieldも0であることを要求する。受理artifactから`EncodedSerializablePathwiseErrorEvidence`が必ず存在し、`WithinBy` contractを加えれば`SerializableIntegerReliabilityReport`を構成できる。従ってerror unitsとrequired unitsは非負で、certifiedならmargin unitsは正になる。canonicalな`-1` reportはsyntax parserだけなら通るが、graphが0を再計算するpathと一致せずfull gateでは拒否され、同じreportにserializable provenanceは存在しない。正しいzero-error artifactはcertified provenanceへ昇格する。未使用fieldが1のoverestimate reportとmode/path shape不一致も拒否する。ただしmargin unitsをtrusted classifierのfloor encodingへ結ぶ義務は別であり、このmoduleだけではmargin inflationを防がない。

`Sprawlens.FixedPointCanonicalMargin`は、その最後のmargin義務をtrusted classifier inputへ接続する。path provenance gateの成功後、report marginが`encodeMarginDown scale actualMargin`と一致する場合だけ最終受理する。成功条件は基礎gate成功とmargin一致の必要十分条件で、`WithinBy`と合わせれば既存の`MarginEncodedSerializableReport`が存在する。actual marginが非負でreportがcertifiedなら、decode後required errorが元のactual marginより真に小さく、任意の既存stability implicationへ渡してtarget一致を得られる。zero-error・actual margin 1のartifactは受理される。一方、真正なboundary pathとnonnegative provenanceを保ったままmarginを1000から1001 unitsへ増やしたartifactは基礎gateを通って偽certifiedになるが、actual margin 1の最終gateでは拒否される。従ってmargin fieldはcanonical decimalであるだけでも、正値であるだけでも足りず、trusted classifier outputからの再計算一致がload-bearingである。

`Sprawlens.FixedPointWireArtifact`は、scale tagもまだ文字列である完全なwire境界を追加する。各numeric fieldは`(scaleDecimal, unitsDecimal)`を持ち、scale側のUTF-8 byte上限を先に検査してから、trusted expected scaleの`Nat.repr`とbyte-for-byte比較する。attacker-controlled scaleを`Nat`や`BigInt`へparseしない。pathはraw step数をscale検査より先に制限し、report三fieldとmode別path全stepがwire検査を通った後だけ、既存のunit canonicality・path provenance・actual margin gateへ進む。成功から既存`MarginEncodedSerializableReport`が存在し、certified target soundnessまで継承する。scale 1000の正例は受理され、`01000`、scale 500、全角`１０００`、scale byte上限3、path側のleading-zero scale、units alias `00`、inflated marginはそれぞれ該当layerで拒否される。typed artifactをwire化するとscale tagはtrusted reprへ正規化されround-tripする。なおtarget/edit自体のserialization byte上限とJSON envelope全体のbyte上限はこのmodelに含まず、production transportで別途必要である。

`Sprawlens.FixedPointWireResourceLimits`は、step数だけでは防げないtarget listの構造的resource境界を置く。reportのselected/best targetと全path stepの`next`について各list長を制限し、それらに現れるedit occurrence総数も独立に制限する。各step targetが長さ`L`以内ならpath側総数は`stepCount × L`以下になる。guardはscale/unit parseとgraph verificationより前に評価され、成功はstructural policy成立と既存wire gate成功の必要十分条件で、policy内では既存結果を完全に保存しtarget soundnessも継承する。三編集の正例はreport二listと一path targetで合計9 occurrencesとなり、個別上限3・総量9で受理される。個別上限2では拒否され、全listが3以内でも総量8なら別途拒否される。後者のartifact自体はcertifiedのままなので、resource refusalを`inconclusive`やinstabilityへ写像しない。Edit一要素のserialized byte sizeとJSON envelope全体は引き続きtransport側の義務である。

`Sprawlens.FixedPointWirePayloadBudget`は、numeric stringの実UTF-8 byte数と、callerが与える各Editのserialized weightを分離してschema payload weightを定義する。report三numeric field、mode別path全step、report/path targetに現れる全Edit occurrenceを加算する。JSON key、quotes、separator、escaping overheadは推測で定数化せず、このweightには含めない。各Edit weightが`B`以下なら、target部分の総weightは既証明のtarget occurrence数×`B`以下になる。structural guardの後、scale/unit parseとgraph verificationの前にschema budgetを検査し、成功条件、policy内完全性、target soundnessを継承した。三編集正例のnumeric bytesは23、Edit occurrenceは9なので、一要素1 byteならexact 32、一要素100 bytesならexact 923となる。32/923の境界では受理、31/922では拒否され、100-byte caseでは`9 × 100`上界がtightである。低budgetでも数学的verdictはcertifiedのままなのでresource refusalは別outcomeである。productionでは実Edit encoderが返すbyte lengthをweightへrefineし、さらに実JSON encoderまたはraw transportの全envelope byte上限を加える必要がある。

`Sprawlens.FixedPointWireValidationLimits`は、wire validator内部に残っていたresource拒否をraw predicateとして抽出する。report三fieldと全path stepのscale/unit UTF-8 byte数、およびmode別pathのstep数をcanonical syntaxやexpected scale一致とは独立に検査する。wire parserとcanonical graph gateを通ってreportが返るなら、このraw predicateが必ず成立することを、wire→serialized report/pathの値保存と各parserのlimit証拠を接続して証明した。従ってpredicate不成立なら既存wire verifierは必ず`none`である。各limitの上向き閉性も証明した。これは実JSON envelope全体のbyte limitではなく、numeric fieldとpath stepに限定したresource contractである。

`Sprawlens.FixedPointWireDiagnostic`は、上のcombined checkerが返す`Option.none`に残っていた意味の潰れを解消する。戻り値を`structuralLimitExceeded | schemaBudgetExceeded | validationLimitExceeded | invalidArtifact | accepted report`へ分け、各constructorの成立条件を必要十分で証明した。判定順はstructural policy、schema budget、raw step/numeric limit、artifact validationである。診断tagを捨てる`toOption`は従来checkerと全入力で一致し、`accepted report`も同じreportの受理と同値なのでtarget soundnessを失わない。三編集artifactは上限内でaccepted、総target量8ではstructural、schema weight 31ではschema、step 0・scale 3 bytes・unit 3 bytesではvalidation-limit refusalになる。十分な全limitを与えたleading-zero scaleだけがinvalid artifactへ到達する。各resource拒否はinvalidと区別され、invalid artifactも幾何のunstable判定ではない。この型に`unstable` constructorは存在しない。production API/UIもtransport policy、payload validation、certificate verdictをtagged unionで保持し、いずれの拒否も`inconclusive`やinstabilityへ変換しない必要がある。

`Sprawlens.FixedPointWirePolicyMonotonicity`は、outer policyの調整が診断結果を壊さない範囲を固定する。target list上限、artifact全体のtarget occurrence上限、schema weight上限はそれぞれ上向きに閉じている。従ってstep数・scale/unit byte上限・validator本体を固定したままこれら三上限だけを緩めると、`accepted report`は同じreportとしてacceptedのままであり、`validationLimitExceeded`とvalidator到達後の`invalidArtifact`もそれぞれ同じ分類を保つ。三編集fixtureでは総量8→9、schema 31→32、step 0→1、scale bytes 3→4、unit bytes 3→4が各refusal→acceptedのexact thresholdになる。acceptedはtarget 4・総量10・schema 100でも保存され、leading-zero scaleはouter上限を緩めてもinvalidのままである。抽象的なaccepted単調性はouter policyに限定され、inner limitを同時変更した一般定理と実encoder envelopeは別義務である。

`Sprawlens.FixedPointWireVerifierMonotonicity`は、上で別義務だったinner limit同時変更のaccepted単調性を閉じる。canonical decimal cost、serialized step list、encoded path checker、report parser、canonical artifact gate、wire scale/path parserの順に、上限拡大後も同じparsed値または同じreportを返すことを証明した。これをouter predicateの単調性と合成し、step、scale bytes、unit bytes、target list、総target occurrence、schema weightの全6上限を同時に増やしても、diagnostic checkerは同じ`accepted report`を返す。fixtureでは`(1,4,4,3,9,32)`の受理が`(2,5,5,4,10,100)`でも保存される。この定理はartifact・trusted margin・cost model・edit weight関数を固定したpolicy単調性であり、weight関数やdecoder、schema、実JSON encoder自体を変更した場合の互換性ではない。

`Sprawlens.FixedPointRawEnvelopeBoundary`は、decode後のschema/canonical sizeと受信raw bytesを分離する。`raw.utf8ByteSize`をdecoder呼出し前に検査し、`envelopeBudgetExceeded | decodeRejected | checked result`を返すgeneric pipelineについて各分岐の必要十分条件、Optionへのtag消去、budget緩和時のdecode rejection/checked保存を証明した。空白を許すdecoderの反例では、raw文字列`" {}"`は3 bytesだがcanonical re-encode`"{}"`は2 bytesなので、post-decode re-encode検査だけではtransport量を抑えられない。wire diagnosticとの合成では9-byte fixtureを境界受理、8 bytesでpre-decode refusal、短いmalformed入力をdecode refusalとして区別し、checked certified reportからtarget soundnessを継承する。これは任意decoderを受け取る抽象contractであり、production JSON decoderが`DecodedWireArtifact`へ正しく対応すること、HTTP decompression前後のどちらをcapするか、実際のbyte buffer計測は引き続き実装/refinement義務である。

`Sprawlens.FixedPointCompressedEnvelopeBoundary`は、最後の曖昧さだったdecompression前後を二つの独立budgetへ分ける。binary transportにも適用できるcaller-supplied `compressedWeight`を先に検査し、decompressor成功後のraw UTF-8 bytesをdecoder前に再検査する。結果は`compressedBudgetExceeded | decompressionRejected | expandedBudgetExceeded | decodeRejected | checked result`で、各分岐の必要十分条件、Option消去、両budget緩和時のdecode rejection/checked保存を証明した。toy反例では1-byte入力`"z"`が3-byte raw`" {}"`へ展開するため、compressed capだけでは展開量を制限できない。wire合成fixtureはcompressed 1 byte・expanded 9 bytesで境界受理し、compressed 0、expanded 8、decompress失敗、decode失敗を別々に分類する。両budgetを2/10へ緩めても同じreportを受理し、certified target soundnessも継承する。実compression format、streaming展開中の早期中止、圧縮率/CPU/memory limit、byte bufferとのrefinementは未証明である。

`Sprawlens.FixedPointStreamingDecompression`は、展開後に全raw文字列を得てから上限検査する前節を、decompressorが生成するchunk列の逐次検査へ精密化する。各chunkにpayloadと抽象work量を持たせ、累積workと累積UTF-8 bytesを独立に検査する。完走は全chunkの合計が両上限内であることと必要十分である。各失敗constructorも、未検査suffixを含む入力分解、受理prefixが上限内であること、次の一chunkを加えた瞬間にworkまたはbyte上限を越えることと必要十分である。失敗後へ任意のsuffixを追加しても、受理prefix・最初の拒否chunk・失敗種別は変わらず、追加分は未検査suffixへ移る。raw文字列は完走時だけmaterializeし、そのbyte数は展開上限以下になる。decoderとwire checkerへ合成し、1 work・9 bytesの境界受理、work 0とbytes 8での最初のchunk拒否、malformed decode拒否、budget緩和時の同一report受理、certified target soundnessを継承した。ただしLean入力は有限chunk列であり、実decompressorが同じ順序・payload・work会計を生成してsuffixを読まずに停止すること、compressed input側のcap、実CPU/memory/ratio policyはproduction refinement義務として残る。

`Sprawlens.FixedPointStreamingProducer`は、有限chunk列を先に構築する仮定を外し、opaque stateへ一回ずつ`pull`して`done | rejected | emit chunk continuation`を得るlazy producer状態機械を置く。pull回数、抽象work、展開UTF-8 bytesを独立に制限し、全outcomeで受理prefixがresource上限内、work/byte失敗では拒否chunkを加えた瞬間だけ該当上限を越え、completed rawは受理chunk連結と一致してbyte上限内になることを証明した。producer observation traceとpull会計を抽出し、completionには`accepted.length + 1`回、resource拒否には`accepted.length + 1`回以下のpullしか使わない。`pullLimitExceeded`、`producerRejected`、`workLimitExceeded`、`expandedBudgetExceeded`、`completed`の全constructorを有限emit trace・pull会計・resource条件と必要十分にした。両resource拒否では、別producerが同じ観測prefixを発行すればcontinuation以後の挙動に依存せず同じ拒否結果になる。有限list producerはpull数`chunks.length + 1`で前節scannerと全入力・全limitについて一致する。decoder/wire checkerへ直接合成し、pull不足、producer拒否、work拒否、byte拒否、decode拒否、境界受理を区別し、certified target soundnessを継承した。これはabstract producer contractであり、production decompressorのstate transition、chunk payload/order、workと実CPUの対応、compressed input/memory/ratio capとのrefinementは未証明である。

`Sprawlens.FixedPointCompressedStreamingProducer`は、compressed transport capと上のlazy producerを一つの境界へ統合する。initializerを呼ぶ前にcompressed byte weightを検査し、展開上限を`min absoluteExpandedCap (maxExpansionRatio × compressedWeight)`とするため、checked rawは絶対byte上限とratio上限の双方を満たす。compressed cap、producer initializer、pull/work/expanded/decode/wire各結果は別tagのまま保持する。checked成立条件をcompressed上限、initializer成功、producer完走、decode成功、wire受理と必要十分にし、全resource上限を緩めても同じchecked resultを保存する単調性を証明した。1-byte入力から9-byte wire artifactを展開するfixtureはabsolute 9・ratio 9で境界受理し、compressed cap 0、initializer失敗、ratio 8、malformed decodeを別々に拒否する。wire certified target soundnessも継承する。実compressed bufferのweight、compression library initializer/pull、workとCPU、allocator memoryとのrefinementは引き続きproduction義務である。

`Sprawlens.FixedPointStreamingResidentMemory`は、展開済みoutput bytesとdecompressor resident stateとchunk生成時のtemporary overheadを別々に会計する。空文字を返すunbudgeted producerはexpanded bytes 0の上限を満たしながらstate weight 100を保持できる反例により、output capだけではresident memoryを上界づけられないことを固定した。予防的境界ではpull前に`maxMemory - retainedOutputBytes`をallowanceとして渡し、`done | rejected | memoryRefused | emit`を返すbudget-aware producer contractを使う。emit contractはcurrent state、chunk payload、next state、temporary overheadの和がallowance以下であることを要求する。従って各honored emissionのpeakと、completed時の`raw UTF-8 bytes + final state weight`がmemory cap以下になる。initial stateが既にcapを越える場合は最初のpull前に拒否する。allowance 1でdone、2でmemory拒否するproducer反例により、memory cap拡大だけから受理単調性は従わない。非memory結果をlarger allowanceでも保存する独立contractを置けば、completionとchecked resultはmemory cap緩和時に保存される。decoder/wire checkerへ合成し、state weight 0の9-byte fixtureはmemory 9で境界受理、memory 8ではemit前の`memoryRefused`、10では同じreportの受理となり、certified target soundnessを継承する。Lean上の`memoryRefused`は意味論上emitより前だが、具体compression libraryがcontinuationやbufferを割り当てる前に同じallowanceを強制できること、state/temporary weightが実allocator resident/peak bytesを上界づけることは未証明のproduction refinement義務である。

`Sprawlens.FixedPointCompressedResidentPipeline`は、分かれていたcompressed transport、absolute/ratio expanded budget、pull/work、resident memory、decode、wire certificateを単一pipelineへ合成する。checked成立はcompressed cap内、initializer成功、budget-aware producer完走、decode成功、wire受理と必要十分である。honored memory contract下のchecked rawについて、`rawBytes ≤ absoluteExpandedCap`、`rawBytes ≤ maxExpansionRatio × compressedWeight`、`rawBytes + finalStateWeight ≤ maxMemory`を同時に証明し、certified target soundnessを継承した。1-byte compressed入力から9-byte wire artifactを得るfixtureはexpanded 9・ratio 9・memory 9で境界受理し、ratio 8ではexpanded refusal、memory 8ではpre-emission memory refusalとなる。これは全resource modelを一つにまとめた抽象contractであり、実buffer weight、compression initializer/pull、CPU work、state/temporary allocator weightへのrefinementはなお必要である。

`Sprawlens.FixedPointStreamingCpuRefinement`は、producerがchunkへ自己申告する`work`とobserved CPU costを分離する。各chunkのobserved workがclaim以下であるrefinementから、observed総和が既存`totalChunkWork`以下になることを証明した。resident runnerの完走ではclaimed workが`maxWork`以下で、accepted chunk数に最後の`done`確認を加えたpull数が`maxPulls`以下になる。従って一pullあたりのobserved overheadが`perPullOverhead`以下なら、合成上界は`maxWork + maxPulls × perPullOverhead`である。この上界をcompressed/ratio/memory統合pipelineの任意checked resultへ接続した。空payload・claim 0のchunkへobserved cost 100を割り当ててもrunnerが完走する反例により、work claimだけではCPUを拘束できない。chunkが0個でもterminal pull overheadは残る。二chunk・claimed work 2・3 pulls・overhead 3では合成上界11がtightになる。ただし`observedWork ≤ claim`とuniform pull overheadは外部instrumentation/refinement仮定であり、Leanはwall-clock time、scheduler、GC、JIT、allocator、library内部処理を測定していない。

`Sprawlens.FixedPointResourceCounterSafety`は、resource上限を有限幅counterへ移植するときの加算順序を固定する。modulus 256のtoy counterではused 255へdelta 2を加えると1へwrapし、数学的合計257がlimit 255を越えるのにadd-then-compareが受理する。対策の`checkedAddWithin`は、まず`used ≤ limit`、次に`delta ≤ limit - used`を検査し、その後だけ`used + delta`を返す。成功は数学的合計がlimit以下であることと必要十分で、返値はexact sum、limitがmachine maximum以下なら返値もmachine range内、limit緩和時には同じ返値を保存する。これをlist accumulatorへ持ち上げ、成功存在と総weight上限の同値、exact total、失敗とstrict overflowの同値、limit単調性を証明した。chunk workとUTF-8 bytesへ特殊化し、二chunkのwork/bytes 2はlimit 2でexactに受理される。これはbounded counter実装の一般contractであり、JS `BigInt`、Rust/MoonBitのchecked arithmetic、特定word sizeやcompiler演算へのrefinement自体ではない。

## 証拠の境界

- Lean theorem: 抽象modelの全入力に対する証明。
- 共有fixture: 現在のTypeScript実装とLean executableが選んだ結果の有限例での一致。
- TypeScript unit test: controlled path builderが具体例でexact endpointを作る回帰検査。

したがって、共有fixture通過をTypeScript実装全体の形式証明とは呼ばない。
